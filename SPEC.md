# Benchmark specification

Version 1. This is the contract every framework implementation follows. Implementations must be
*equivalent*: for every scenario they read and write the same rows and return the same values. Where a
framework can't do something the idiomatic way, the implementation declares the scenario unsupported
rather than approximating it.

The shared code in `common/` encodes this spec: schema (`common/src/main/resources/bench/schema.sql`),
seed data (`bench.common.dataset.Seed`), scenario inputs (`bench.common.scenario.*`), JMH benchmark
classes (`bench.common.jmh.*`) and the correctness checks (`common/src/testFixtures`). If this document
and the code disagree, that's a bug; fix whichever is wrong in the same change.

## 1. Database

- PostgreSQL, image `postgres:18.6` (pinned in `gradle/libs.versions.toml`). One server per benchmark
  session, shared by all implementations, run with:
  `shared_preload_libraries=pg_stat_statements`, `max_connections=200`, `synchronous_commit=off`.
  `synchronous_commit=off` keeps WAL flush latency (a property of the disk, not of the framework) from
  dominating write scenarios. `fsync` stays on.
- Isolation: the server default (READ COMMITTED). Implementations must not set an isolation level.
- The schema is created and seeded by `common` through plain JDBC, never by a framework. Frameworks
  run with schema generation/validation disabled.
- Before each JMH fork (trial), the database is *reset*: every row created by write scenarios is
  deleted, mutable rows are restored to their seed values, then `VACUUM ANALYZE` runs. Every benchmark
  therefore starts from an identical database state.

## 2. Schema

```
author        (id BIGINT IDENTITY PK, name VARCHAR(100), country CHAR(2))
book          (id BIGINT IDENTITY PK, author_id BIGINT FK -> author, title VARCHAR(200),
               isbn VARCHAR(32) UNIQUE, pages INT, price NUMERIC(10,2), published_on DATE)
               index on author_id
purchase_order(id BIGINT IDENTITY PK, reference UUID UNIQUE, customer VARCHAR(100),
               created_at TIMESTAMP WITH TIME ZONE)          index on customer
order_line    (id BIGINT IDENTITY PK, order_id BIGINT FK -> purchase_order, line_no INT,
               product VARCHAR(100), quantity INT, unit_price NUMERIC(10,2))
               unique (order_id, line_no)
stock_item    (id BIGINT IDENTITY PK, sku VARCHAR(32) UNIQUE, quantity INT, version INT)
```

All columns are `NOT NULL`. Identity columns are `GENERATED BY DEFAULT AS IDENTITY`: the seed inserts
explicit ids, then moves each identity past the seed range. New rows get database-generated ids.

Mapping expectations:

- `book.author_id` is mapped as a plain `Long authorId` attribute, not as an association. No scenario
  navigates book → author, and a plain column maps identically in every framework.
- `purchase_order` → `order_line` is a one-to-many owned by the order (an aggregate). Mapping may be
  uni- or bidirectional, `List` or `Set`, whatever is idiomatic for the framework; line order in a
  loaded order is unspecified (checks sort by `line_no`). `line_no` is an ordinary column.
- `purchase_order.reference` is a `java.util.UUID`, `created_at` a `java.time.Instant`.
- `stock_item.version` is the optimistic-locking version attribute (`@Version`).
- Ids are always database-generated (identity) for new rows. Implementations must not switch to
  sequences or client-generated ids.

## 3. Dataset

Deterministic, fixed row counts (`bench.common.dataset.Seed` has the exact formulas):

| Table | Rows | Layout |
|---|---|---|
| author | 100 | ids 1..100, `name = "Author %03d"`, country cycles US, GB, DE, FR, RS |
| book | 12,070 | author 1: ids 1..10 (10 books); author 2: ids 11..110 (100); author 3: ids 111..10110 (10,000); authors 4..99: 10 each, ids 10111..11070; author 100: ids 11071..12070 (1,000 *mutable* books, the only seeded books write scenarios modify) |
| purchase_order | 1,000 | ids 1..1000, 10 orders per customer, `customer = "customer-%03d"` of `(id-1)/10` |
| order_line | 5,000 | 5 lines per order, `line_no` 0..4 |
| stock_item | 1,000 | ids 1..1000, `quantity = 1,000,000`, `version = 0` |

Book attributes for id `i`: `title = "Book %05d"`, `isbn = "ISBN-%08d"`, `pages = 50 + (i*37) % 950`,
`price = 5.00 + ((i*53) % 4500) / 100`, `published_on = 2000-01-01 + (i*17) % 9000 days`.

New rows created by write scenarios always belong to author 100 (books) or to customer
`"bench-writer"` (orders), so they never change the result of a read scenario.

## 4. Scenarios

Each scenario has an id (also the JMH method name), a group, and an exact definition. "Returns" is what
the implementation's scenario method returns; the correctness check compares it with the expected
value derived from the seed. Inputs rotate deterministically per benchmark thread (see
`bench.common.scenario.Workload`) so no framework-level cache can serve repeated identical requests.

Unless stated otherwise, reads run without an explicit transaction (if the framework opens one by
default, that is part of its measured cost). Each write scenario must be atomic: one database
transaction, or a single statement in auto-commit.

### 4.1 Reads (blocking, group `reads`)

| Id | Operation | Returns |
|---|---|---|
| `findById` | Load one book by primary key. Ids rotate over author 3's books. | the book |
| `findByIsbn` | Finder on a unique non-key column (`isbn`), derived query where available. | the book |
| `list10`, `list100`, `list10000` | All books of author 1 / 2 / 3, `ORDER BY id`. | 10 / 100 / 10,000 books, in order |
| `projection` | DTO projection `(id, title, price)` of author 2's books, `ORDER BY id`. Must select only those columns (a class/record DTO, not an entity or a dynamic proxy). | 100 summaries |
| `pageWithCount` | Offset page of author 3's books: page index 2, size 20, `ORDER BY id`, plus total count (framework `Page` type). | ids 151..170 and total 10,000 |
| `sort` | Author 2's books with a *dynamic* sort passed at runtime: `price DESC, title ASC`. | 100 books |
| `keysetPage` | Keyset (cursor) page of author 3's books `ORDER BY id`, 20 rows after id 1110, no total count. Must use the framework's cursor/keyset API; unsupported otherwise. | ids 1111..1130 |
| `inList1000` | Books whose id is in a list of 1,000 ids (`111 + 10k`, k = 0..999). | 1,000 books, any order |
| `criteria` | Dynamic query built at runtime with the framework's criteria/specification API from a filter object: `author_id = 3 AND pages BETWEEN 500 AND 520 AND price < 20.00`, `ORDER BY id`. Null filter fields must be skipped (the API must be dynamic). | the matching books |
| `joinFetch` | All orders of `customer-007` with their lines, `ORDER BY order id`, lines fully loaded. Fetch strategy is the framework's idiomatic one (join, entity graph, separate queries); the statement count shows the difference. | 10 orders × 5 lines |

### 4.2 Writes (blocking, group `writes`)

| Id | Operation | Returns |
|---|---|---|
| `save` | Insert one new book (author 100) through the repository `save`. | generated id |
| `saveAll100`, `saveAll1000` | Insert 100 / 1,000 new books through the repository `saveAll` (batching is allowed and encouraged if the framework does it). Atomic. | generated ids in input order |
| `update` | In one transaction: load a mutable book (author 100) by id, change its price, save. | the updated book |
| `delete` | Delete one book by id through the repository. The row is inserted by the harness (plain JDBC, outside the measured time) before each invocation. | nothing |
| `cascadeInsert` | Insert one order with 5 lines in one repository `save` using the framework's cascade. | generated order id |
| `optimisticUpdate` | In one transaction: load a stock item, decrement quantity, save; the `UPDATE` must check and increment `version`. | the updated item |

### 4.3 Transactions (blocking, group `tx`)

All use the framework's declarative transaction support where it has one (annotations), and nested
calls go through a separate bean/service so the declarative boundary actually applies.

| Id | Operation | Returns |
|---|---|---|
| `txReadOnly` | Read-only transaction: `findById` of two books. | both books |
| `txReadWrite` | Read-write transaction: `findById` of one book, then `save` of a new book. | new id |
| `txNestedRequired` | Outer REQUIRED transaction: `findById`; inner method (another bean) with REQUIRED: `save`. One physical transaction. | new id |
| `txRequiresNew` | Outer REQUIRED transaction: `findById`; inner method (another bean) with REQUIRES_NEW: `save`. Two physical transactions. | new id |
| `txRollback` | Read-write transaction: `save` of a new book, then throws `IntentionalRollbackException`; the transaction rolls back and the exception reaches the caller. | (exception) |

Check-only semantics (verified by the correctness check, not benchmarked): REQUIRES_NEW work survives
an outer rollback, nested REQUIRED work is rolled back with the outer transaction, and a save with a
stale `version` fails with `OptimisticConflictException`.

### 4.4 Reactive (group `reactive`, R2DBC implementations)

Same semantics as the blocking counterpart; results are consumed element by element from a
`org.reactivestreams.Publisher` (streamed, never collected by the implementation).

| Id | Blocking counterpart |
|---|---|
| `reactiveFindById` | `findById` |
| `reactiveStream10`, `reactiveStream100`, `reactiveStream10000` | `list10`, `list100`, `list10000` |
| `reactiveSaveAll100`, `reactiveSaveAll1000` | `saveAll100`, `saveAll1000` (atomic) |
| `reactiveTxUpdate` | `update`, inside a reactive transaction |
| `reactiveTxRollback` | `txRollback`: the publisher signals `IntentionalRollbackException` after rollback |

### 4.5 Concurrency

Selected scenarios (`findById`, `list100`, `update`, `txReadWrite`, and `reactiveFindById` /
`reactiveTxUpdate` for reactive implementations) are run with 1, 16 and 64 platform threads and with 64
virtual threads (JMH `-Djmh.executor=VIRTUAL`). The connection pool size stays fixed at 16, so 64 threads
measure behaviour under pool contention. Each thread updates its own slice of mutable rows, so `update`
has no row-lock contention between threads.

### 4.6 Startup and memory

Process-level, outside JMH (`runner/bench.py startup`): start a fresh JVM, start the framework
(including the connection pool), execute the first `findById`, and report:

- time to first query: wall time from process launch to the "ready" line, measured by the harness;
- RSS after the first query (`ps`), and peak RSS (`/usr/bin/time`);
- each repeated N times (default 10), median and max reported.

Native image: not in phase 1 (see `DESIGN_NOTE.md`).

## 5. Categories

Every implementation declares one category; results are only compared within a category, with the
baseline of the same access style as the lower bound.

| Category | Meaning | Phase 1 members |
|---|---|---|
| `baseline-jdbc` | hand-written JDBC, lower bound for blocking | plain-jdbc |
| `sql-mapping` | repositories generating SQL without an ORM session | micronaut-data-jdbc, spring-data-jdbc |
| `orm-jpa` | JPA/Hibernate-based repositories | micronaut-data-jpa, spring-data-jpa |
| `reactive` | R2DBC-based repositories | micronaut-data-r2dbc, spring-data-r2dbc |
| `baseline-r2dbc` | hand-written R2DBC, lower bound for reactive | (phase 2) |
| `kotlin` | Kotlin-first frameworks (Exposed, Komapper, jOOQ-Kotlin…) | (phase 2) |
| `document` | MongoDB document mapping | (later) |

## 6. Metrics

| Metric | Source | Notes |
|---|---|---|
| ops/s | JMH `Throughput` mode | primary metric |
| p50 / p99 latency | JMH `SampleTime` mode | |
| allocation per op | JMH `-prof gc` (`gc.alloc.rate.norm`, B/op) | includes harness allocation, identical for all |
| SQL statements per op | `pg_stat_statements` (`calls`), separate counting pass | data statements (`SELECT`/`INSERT`/`UPDATE`/`DELETE`, plus any `SET`/`SHOW`) *executed* by the server; a JDBC batch of N inserts counts N; harness statements and the drivers' connection set-up statements (pgjdbc `SET application_name`; r2dbc-postgresql `SHOW TRANSACTION ISOLATION LEVEL` and its `pg_type` lookup) are excluded. Not round trips. |
| transaction control per op | same pass, reported separately | `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` as recorded by `pg_stat_statements`. A lower bound only: the server records e.g. `BEGIN READ ONLY` but not the `BEGIN`/`COMMIT` pgjdbc sends through the extended protocol. |
| time to first query, RSS, peak RSS | startup harness | JVM only in phase 1 |

## 7. Fairness rules

1. Same database server, version, configuration and dataset for every implementation in a session.
2. Same JDBC driver (`org.postgresql:postgresql`), R2DBC driver (`org.postgresql:r2dbc-postgresql`),
   pools (HikariCP for JDBC, `r2dbc-pool` for R2DBC) and Hibernate version. These are pinned in
   `gradle/libs.versions.toml` and forced onto every framework's dependency graph, overriding the
   framework BOMs. The JDBC URL carries no extra driver parameters.
3. Pool: 16 connections, fixed (minimum idle = maximum = 16; R2DBC initial = max = 16). Configurable
   with `BENCH_POOL_SIZE` for experiments, but published results use 16.
4. Same JDK and JVM flags for every implementation (default `-Xms2g -Xmx2g -XX:+UseG1GC` for JMH,
   `-Xmx512m` for startup runs). The runner records both.
5. JMH: at least 3 forks, fixed warm-up (default 5 × 2 s) and measurement (5 × 2 s) for published runs.
6. Two configurations per implementation: `default` (the framework's defaults, only what's required
   to connect and to disable schema generation) and `tuned` (documented settings that a knowledgeable
   user would apply). Both are published as files in the implementation, and each result names its
   configuration. If an implementation has no meaningful tuning, `tuned` is identical to `default`
   and says so.
7. Every result records the resolved dependency versions of the implementation (for snapshots, the
   exact timestamped version), the git SHA of this repository, and the environment (CPU, cores, OS,
   JDK, database version, JVM flags).
8. An implementation must pass the shared correctness check, in both configurations, before it is
   benchmarked.
9. Logging at WARN for framework packages, to the console; no SQL logging; no metrics, tracing or
   web server.
10. Laptop, cloud and shared-CPU machines are for development only. Published numbers need a quiet,
    dedicated machine with the environment recorded.

## 8. Implementation contract (for framework authors)

An implementation is a Gradle project under `frameworks/<name>/` that applies the `bench.implementation`
convention plugin and provides:

1. a `bench.common.spi.TargetFactory` registered with `ServiceLoader`
   (`META-INF/services/bench.common.spi.TargetFactory`). It returns `ImplementationInfo` (id, framework,
   category, configurations, unsupported scenarios) and starts a `BenchmarkTarget` for a given
   configuration and database;
2. `BlockingScenarios` and/or `ReactiveScenarios` implemented with the framework's idiomatic API
   (repositories, declarative transactions), returning the framework's own entities (they implement
   the `bench.common.model` view interfaces) without copying;
3. an empty JMH subclass of `bench.common.jmh.BlockingBenchmark` and/or `ReactiveBenchmark`;
4. a JUnit test extending `bench.common.check.BlockingCorrectnessCheck` and/or
   `ReactiveCorrectnessCheck`;
5. its `default` and `tuned` configuration files.

Scenarios that the framework can't express idiomatically throw `UnsupportedScenarioException` and are
listed in `ImplementationInfo.unsupported()`; the correctness check enforces that the two agree.

## 9. Result format

`runner/bench.py` writes `results/<timestamp>/`:

- `run.json`: `environment` (CPU, cores, OS, JDK, JVM flags, database version and settings, git SHA,
  runner options), `implementations` (per implementation: info, configuration, resolved versions) and
  `results`: one record per (implementation, configuration, scenario, mode, threads, executor) with
  `score`, `error`, `unit`, `p50`, `p99`, `allocBytesPerOp`, `statementsPerOp`, `txControlPerOp`;
- `results.csv`: the same records flattened;
- `raw/`: JMH JSON, statement counts and startup measurements as produced.
